Build a High-Concurrency Event Ticketing System using a Next.js App Router and a Polyglot Persistence architecture (PostgreSQL, MongoDB, and Redis). 

I have already added the following environment secrets: `MONGODB_URI`, `UPSTASH_REDIS_REST_URL`, and `UPSTASH_REDIS_REST_TOKEN`. Please provision a Replit PostgreSQL database for the relational data.

Here is the exact technical specification you must follow:

1. TECH STACK & DEPENDENCIES
- Frontend & Backend: Next.js App Router, React, Tailwind CSS.
- Relational DB: PostgreSQL (Use raw SQL via the `pg` package. Do not use an ORM).
- Non-Relational DB: MongoDB (Use the native `mongodb` package).
- Cache/Concurrency DB: Redis (Use `@upstash/redis`).
- Auth: NextAuth.js (Credentials provider with `bcrypt` for password hashing).

2. POSTGRESQL ARCHITECTURE (Strict ACID Data)
Create a `db/schema.sql` file and an initialization script to set up the following:
- Tables:
  - `users`: user_id (UUID PK), name, email (UNIQUE), password_hash, role (VARCHAR default 'Customer').
  - `venues`: venue_id (UUID PK), name, total_capacity, location.
  - `events`: event_id (UUID PK), venue_id (FK), title, start_time, base_price, available_seats.
  - `bookings`: booking_id (UUID PK), user_id (FK), event_id (FK), seat_number, status (VARCHAR 'PENDING', 'SUCCESS', 'FAILED').
- Advanced Database Features (Mandatory for project requirements):
  1. Constraints: Add CHECK constraints (e.g., base_price >= 0) and strict Foreign Key constraints (ON DELETE RESTRICT).
  2. Indexes: Create a composite UNIQUE index on `(event_id, seat_number)` where status = 'SUCCESS'.
  3. View: Create `event_sales_summary_view` joining events, venues, and bookings with GROUP BY to show total revenue and tickets sold per event.
  4. Trigger: Create a trigger function that automatically decrements `available_seats` in the `events` table whenever a new booking is inserted with the status 'SUCCESS'.
  5. Stored Procedure: Create a PL/pgSQL function to handle the transactional insertion of a booking.

3. MONGODB ARCHITECTURE (Flexible Data)
Set up a connection utility using `MONGODB_URI`.
- `event_details` collection: Stores dynamic JSON metadata (cast, faqs, tags, image URLs).
- `reviews` collection: Stores user reviews (event_id, user_id, rating, comment).

4. REDIS CONCURRENCY LOGIC (Seat Locking)
- When a user selects a seat, create an API route that uses Upstash Redis to set a lock: `SET lock:event_{id}:seat_{num} {user_id} EX 300 NX`. This creates a strict 5-minute temporary lock to prevent race conditions.

5. CORE PAGES & FEATURES TO BUILD
- Authentication: Login and Register pages.
- Homepage: Fetches upcoming events (combining base data from Postgres with images/metadata from MongoDB).
- Seat Map & Checkout UI: 
  - A dynamic seat grid where locked seats are greyed out. 
  - A mock checkout modal with two explicit testing buttons: "Simulate Payment: SUCCESS" and "Simulate Payment: FAILURE".
- Checkout API Route: 
  - On SUCCESS: Execute a Postgres transaction committing the booking, then delete the Redis lock key.
  - On FAILURE: Rollback Postgres, and delete the Redis lock key immediately so the seat is freed.
- Admin Dashboard (Protected Route): Displays the `event_sales_summary_view`. Include an API route and a UI button that allows the admin to download the summary table as a CSV file.
